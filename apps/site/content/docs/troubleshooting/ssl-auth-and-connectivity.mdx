## What to check first

- Whether the repository is reachable outside the app
- Whether the server presents a certificate chain your machine trusts
- Whether stored credentials are valid for the exact repository path

## Good evaluation practice

Validate SSL and authentication behavior early in a rollout, especially for older on-prem SVN infrastructure.

## If prompts repeat

Treat repeated prompts as a signal to investigate certificate trust, URL mismatch, or credential scoping before retrying the same operation indefinitely.

## ShellySVN and TortoiseSVN use two credential stores

On Windows, ShellySVN can use credentials from two places:

1. **ShellySVN saved credentials** are encrypted with Electron `safeStorage` and kept in the app's `auth-cache.json` under its Electron user-data directory.
2. **Native Subversion credentials** are kept in Subversion's client cache. This is normally the Windows-encrypted login TortoiseSVN uses.

When a matching ShellySVN credential exists, ShellySVN passes it explicitly to `svn`. It therefore takes precedence over the native cache. A stale ShellySVN password can produce `E215004` even while the same repository continues to work in TortoiseSVN. Removing the ShellySVN entry allows Subversion to fall back to its native cache.

The Saved Credentials page is the supported place to remove the app entry. The `settings.savedCredentials` value in `shellysvn-config.json` is legacy metadata and is not the authoritative credential store. Do not paste or share `auth-cache.json`: although passwords are encrypted, the file contains sensitive repository and account metadata.

### Diagnose a dev-build mismatch safely

Run these checks from the same Windows account that launches `bun dev`:

```powershell
# Confirm which client the shell resolves.
Get-Command svn.exe
svn --version --quiet

# List native realms and usernames. Passwords are not printed.
svn auth

# Verify native-cache authentication without putting a password in arguments.
svn info 'https://svn.example.com/svn/repository' --non-interactive
```

Also check **Settings → Subversion** for a configured client path. A development build may use ShellySVN's bundled `svn.exe` instead of the executable returned by `Get-Command`; run the same `info` probe with that exact executable when comparing behavior.

Use the command log to distinguish the paths:

- `--username … --password-from-stdin` means ShellySVN injected a saved credential.
- No username or password option means Subversion was allowed to use its native cache.

Never add a password directly to a diagnostic command. Avoid `--password <value>`, shell history, screenshots containing revealed credentials, and copied logs containing secrets. Repository diagnostics show only the attempted username, password length, and an edge-whitespace warning.

If Settings reports that deletion succeeded but the next command still injects the same credential, fully restart the dev main process and check the Saved Credentials page again. Credential list/delete/clear operations must wait for the encrypted cache to load and for changes to reach disk; a regression in that ordering is the first place to investigate.

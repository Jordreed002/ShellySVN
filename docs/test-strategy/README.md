# ShellySVN Test Strategy

This folder is the single source of truth for **what we test and why**. It keeps
test coverage anchored to real user value (journeys) rather than to
implementation details, and it gives a living inventory of every test in the
codebase.

## Contents

| File                                     | Purpose                                                                                                                                                                             |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`user-journeys.md`](./user-journeys.md) | The 14 user journeys (J1–J14) that drive all test design. Each journey lists steps, the IPC channels/components involved, current coverage, and the remaining gap. Read this first. |
| [`test-tracker.csv`](./test-tracker.csv) | The **spreadsheet** — one row per test case (journey, layer, area, file, suite, name, status). Open in Excel / Numbers / Google Sheets. Auto-generated; do not hand-edit.           |
| [`test-tracker.md`](./test-tracker.md)   | Human-readable summary of the CSV: snapshot totals, coverage by journey, the planned-gap backlog, and a layer/area breakdown.                                                       |

## Keeping the tracker in sync

The tracker is regenerated by scanning the codebase — **re-run it whenever you add
or rename a test**:

```bash
node scripts/generate-test-tracker.mjs
```

It writes both `test-tracker.csv` and `test-tracker.md`. New tests are tagged
with a journey automatically via the path-keyword classifier in the script; if a
test lands in "Uncategorized", extend the `classify()` rules.

## Layering rules

- **Unit / integration / perf tests** own the logic edge cases (parsing, caching,
  auth flows, mutation queuing, error classification). Fast, deterministic, no
  Electron. Run with `bun run test:unit`.
- **E2E tests** (`tests/e2e/*.spec.ts`) chain steps into journeys and assert
  _outcomes_, not just that a control exists. They launch the real built app
  (`out/main/index.js`) via Playwright. Run with `bun run test:e2e`.
- Every new test should map to a journey in `user-journeys.md`.

## Known weaknesses (tracked, not blocking)

- **1 network-dependent `.real` test** (`svn-release-workflows.real.test.ts`)
  commits over a locally-spawned `svnserve` and can flake with
  `E210002 Network connection closed unexpectedly` when the daemon isn't ready.
  It is `hasSvnServe()`-guarded but the guard doesn't cover mid-run daemon drops.
- **E2E test isolation (resolved)**: the Electron app previously persisted its
  settings store between test runs, leaking state from one spec into the next.
  The fixture now gives each test a clean `--user-data-dir` (created and removed
  per test), so launches are isolated.
- **Systemic dialog accessibility gap (open)**: there are two dialog families.
  The newer `features/repo-browser/components/*` dialogs wrap in
  `AccessibleDialog` (Escape-to-close + focus trap). The legacy
  `components/ui/*Dialog.tsx` family — Settings, Commit, Checkout, AddRepo, and
  ~30 others — render a plain `.modal-overlay` and so lack both behaviors.
  Pressing Escape does not close them and Tab focus escapes into the UI behind.
  This is the work the roadmap's "1.3 a11y" milestone covers; it is tracked
  in-code as `test.skip` in `tests/e2e/keyboard-interactions.spec.ts`.
- **E2E coverage is structural-leaning**: many specs assert "button is
  accessible" / "dialog can be opened". The `user-journeys.spec.ts` and
  `keyboard-interactions.spec.ts` files are the start of the move toward
  outcome-asserting journeys; the gap backlog in `test-tracker.md` lists more.
